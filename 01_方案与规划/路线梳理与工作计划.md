### 结论：交付形态 = WorkBuddy 可运行网页智能体（Python 零依赖）

理由很硬：

1. **代码已经在跑了**。02_ 里是一个可 `python web_app.py` 直接体验的网页智能体（含订单/任务台账面板），自测全过。这是今天真正能演示、能交付的东西。
2. **零成本、零门槛**。Python 原型由队长+AI 在本环境维护即可；未配 Key 自动走 Mock 演示模式，配了 `DEEPSEEK_API_KEY` 走真实抽取。
3. **评委看的是"智能体能否干活"**，不是"跑在哪个平台"。WorkBuddy 网页本身就是可体验智能体，配录屏双保险，满足官方"可体验智能体或运行演示 + 说明"要求。
4. 官方明说"不强制从零写全部代码、可用通用框架"。我们自研了抽取/校验/变更/查询/简报全部逻辑，披露清晰即可。

### 端到端管线

```
业务群聊(粘贴/文本)
   │
   ▼
[输入层]  网页聊天框 / CLI / 测试注入
   │
   ▼
[抽取层]  LLM(JSON 结构化)  ← 未配 Key 走 Mock，配了 DEEPSEEK_API_KEY 走真实
   │
   ▼
[规则层]  确定性校验 + 变更比对 + 缺失/冲突/异常判定  ← 当前只做到前两项
   │
   ▼
[存储层]  本地 JSON 台账(order.json / task.json)
   │
   ▼
[编排层]  意图路由：提取入库 / 随口查单 / 今日简报
   │
   ▼
[展示层]  聊天回复(带原文依据) + 右侧实时台账面板 + 简报
```

## 四、系统架构方向（分层与职责）

代码已自然分好层，建议**固定这套分层**不再重构（10.21 后只加不改结构）：

| 层    | 文件                       | 职责                                                  |
| ---- | ------------------------ | --------------------------------------------------- |
| 配置   | `config.py`              | Key 走环境变量，缺省 Mock；支持 DeepSeek / 任意 OpenAI 兼容        |
| 模型封装 | `llm.py`                 | 零依赖 HTTP 调用，JSON 模式                                 |
| 提示词  | `prompts.py`             | 抽取/查询/简报 System + 卡片/查询/简报文案 + 状态序                  |
| 存储   | `store.py`               | JSON 台账：增/改/查/过滤，等价两张数据表，**核心资产，稳**                 |
| 抽取   | `extractor.py`           | LLM→JSON，Mock 透传                                    |
| 规则   | `validator.py`           | 校验 + 变更比对，**确定性逻辑放这里**（防幻觉关键）                       |
| 编排   | `agent.py`               | `parse_chat/query/briefing` + `handle_message` 意图路由 |
| 入口   | `web_app.py` / `main.py` | 网页(标准库 HTTP) / CLI                                  |
| 前端   | `static/index.html`      | 聊天+双台账面板                                            |
| 数据   | `sim_chats.py`           | 模拟群聊 + Mock 抽取                                      |
| 自测   | `test_pipeline.py`       | 全链路断言（当前 5 条断言）                                     |

**架构要点**：所有"可能误判"的活交给确定性代码（`validator.py`），LLM 只做"理解原文→出结构化 JSON"。这是抗评委挑刺的核心设计，必须保持。

## 五、订单与任务处理关键逻辑（重点说明）

### 1. 抽取（理解原文）

- LLM 按固定 JSON Schema 输出 `list[dict]`，字段缺失填 `null` 不编造。
- 两条变更线索关键词："改成/变更为/加到"视为变更。

### 2. 校验（确定性兜底，当前已落地）

- `qty` 转 int 失败→`None`；`delivery_date` 正则 `^\d{4}-\d{2}-\d{2}$` 不符→`None`。
- 订单缺 `customer` 或 `product`→丢进 `skipped`，回复提示"有 N 条信息不全待人工确认"。

### 3. 变更比对（增量更新，当前已落地，是亮点）

- 入库前 `store.find_active(同客户+同产品 且 状态≠已交付)` 命中已有单。
- 命中→**仅覆盖本次有值字段**，old→new 追加进 `changes` 履历（time/field/old/new/source）。
- `status` 取更高阶段（沟通中<已报价<已确认<生产中<已交付），**只进不退**，回退需原文明确。
- 未命中→`INSERT` 新单。
- 实测：NMX-60 数量 5000→6000，`changes` 正确留痕。

### 4. 查询（防幻觉，当前已落地）

- 口语问题→解析客户/产品/状态/时间区间→`customer LIKE` 模糊匹配。
- 0 条→引导换称呼或查全部在途。
- ≥1 条→每条结论后强制附 `📎 依据："{source_excerpt}"`，只陈述台账事实。

### 5. 简报（数值全来自台账，当前已落地）

- 新增(今日创建) / 待报价(status=沟通中) / 临期(交期≤3天且未交付) / 逾期任务(待办且 deadline<今天)。
- LLM 不得编数，全部由 `store.query_*` 计数。

### 6. 缺失 / 冲突 / 异常（**必须补的三块**，当前缺口）

- **缺失追问**：除订单缺客户/产品外，还需识别"任务无 owner/无 deadline → 自动生成追问话术"。
- **冲突检测**：同一单多轮/多源说法不一（数量、交期、责任人矛盾）→ 标红 + 给出澄清建议。实现建议：抽取结果内部两两比对，或新消息与库内同单比对字段不一致且非"明确变更"时判为冲突。
- **异常拦截**：负数数量、过去的交期、明显不合理（如 qty>某阈值）→ 拦截并在回复里说明原因，不入库。
