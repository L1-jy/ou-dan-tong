# 接口与模块对接约定（开工前必须对齐）

> 协作模型：每位队友各开自己的 WorkBuddy，连接同一 GitHub 仓库（[https://github.com/Ruan1027/ou-dan-tong），推各自分支](https://github.com/Ruan1027/ou-dan-tong) → 队长审 PR 合并（见 `COLLAB_GUIDE.md`）。  
> 本文档目的：**在任何人写代码前冻结公用接口与契约**，让模块并行开发不冲突、集成不返工、队长审 PR 只查"是否守约"而非"逻辑对不对"。  
> 原则：**契约冻结后只许加字段（向后兼容），不许改既有字段名/类型。**

---

## 一、必须冻结的 5 个契约

### 1. 聊天输入格式（模块一 ↔ 模块二）

模拟数据（模块一·队友 A）与抽取器（模块二·队友 A）之间的第一道缝。

一条消息统一为：

```json
{
  "group": "客户群名",
  "speaker": "发言人",
  "time": "2026-10-20 14:30",
  "text": "原始口语化聊天内容"
}
```

- 队友 A 的模拟数据（模块一）**必须按此结构提供**，extractor 直接消费。
- 数组即一次群聊记录；动态演进 = 同一 group 下多条按时间排序的消息。

### 2. 变更片段 schema（extractor 输出 · 队友 A 定）

```json
{
  "entity_type": "order | task",
  "entity_id": "订单/任务标识（客户名或单号，允许暂缺）",
  "field": "要变更的字段（如 数量/交期/状态）",
  "old_value": "旧值（新建时为 null）",
  "new_value": "新值",
  "confidence": 0.0~1.0,
  "raw": "命中该变更的原文片段"
}
```

### 3. 订单 / 任务记录 schema（store · 队友 D 定）

- `OrderRecord` 字段：`id, customer, items[], quantity, price, delivery_date, status, change_log[]`
- `TaskRecord` 字段：`id, title, owner, due, status, change_log[]`
- `change_log[]` 每项：`{time, speaker, field, old, new, raw}`（审计留痕，支撑"返回最新而非旧版"）

### 4. 校验结果 schema（validator · 队友 A 定）

```json
{
  "status": "ok | missing | conflict | abnormal",
  "message": "给用户的说明话术",
  "patch": "可应用的变更（ok 时非空）"
}
```

### 5. 查询接口（agent · 队友 C 定）

- `query(entity_id) -> 最新 OrderRecord / TaskRecord`（必须返回最新状态，非历史旧版）
- `brief() -> 日报简报文本`

## 二、单一真相源：contracts.py（建议新建）

把上面 **2/3/4** 的 schema 集中到 `02_智能体代码/ou_dan_tong/contracts.py`，所有人 `import`。

- 原 `schema.py` 已删，重建为契约模块，避免各模块各写各的导致漂移。
- **命名说明**：契约模块本名 `types.py`，但 Python 标准库自带同名 `types` 模块（解释器启动即缓存，本地
  `types.py` 永远无法覆盖它）。经实测确认后重命名为 `contracts.py`，**功能与契约内容完全不变**，已在
  《ou_dan_tong/README.md·模块二》备案。
- **归属**：队友 A 主笔；任何字段改动必须走 PR 且全员确认（向后兼容原则）。
- 队友 D 的 store、队友 C 的 query 一律引用 `contracts.py` 的定义，不得本地另定义同义结构。
