# 瓯单通 · 可复用核心规范（平台无关）

> 来源：团队方案文档与已落地的 Python 原型。
> 用途：沉淀平台无关的核心规范（抽取/校验/变更/查询/简报），WorkBuddy 开发直接复用本文件。

## 1. 项目定位
- 一句话：不换系统、不改习惯，把散落在微信群里的订单和任务，自动变成一张实时、可查询、可提醒的协同台账。
- 用户：温州中小制造/贸易企业（机械配件、电气、鞋服等）的老板娘、业务员、跟单员——无 ERP 或 ERP 无"沟通"环节。
- 项目名：**瓯单通**（瓯江的"瓯" + 订单）。

## 2. 五大能力（P0/P1/P2）
| # | 能力 | 用户动作 | 智能体行为 | 优先级 |
|---|---|---|---|---|
| A | 消息→结构化订单 | 粘贴群聊记录 | 提取客户/产品/规格/数量/单价/交期/特殊工艺，生成订单卡片入库 | P0 |
| B | 订单状态随口查 | "XX 家那单到哪了？" | 查库回答当前状态（沟通中→已报价→已确认→生产中→已交付），引用原文依据 | P0 |
| C | 任务提取与跟进 | 同一段沟通 | 生成任务清单（事项/责任人/期限/关联订单），到期提醒 | P1 |
| D | 变更捕获 | 客户在群里改数量/交期 | 识别变更→更新订单→留变更履历（谁/何时/改了什么） | P1 |
| E | 今日协同简报 | "出今天的简报" | 汇总：新增 N 笔、待报价 N 笔、临期交付 N 笔、逾期任务 N 项 | P2（演示加分） |

时间不够砍 E，保 A/B/D。

## 3. 数据模型（本地 JSON Store）
**order（订单表）**
- order_id(String, PK, 格式 ORD-YYYYMMDD-序号)
- customer(String, 客户简称如"万博机电")
- product(String) / spec(String 型号规格)
- qty(Integer) / unit_price(String 允许"待报价")
- delivery_date(String YYYY-MM-DD, 可空)
- status(枚举：沟通中/已报价/已确认/生产中/已交付)
- sample_flag(String 打样/大货/无)
- source_excerpt(String ≤100字 溯源)
- changes(JSON 数组 [{time, field, old, new, source}])
- created_at / updated_at(String 时间戳)

**task（任务表）**
- task_id(String PK, TSK-YYYYMMDD-序号)
- content(String) / owner(String 可空=待认领)
- deadline(String YYYY-MM-DD 可空)
- order_id(String 关联 可空)
- status(String 待办/已完成)

## 4. 抽取 Schema（LLM 输出 JSON 数组，缺失填 null）
```json
[{
 "type": "order" | "task",
 "customer": "公司简称", "product": "", "spec": "", "qty": null,
 "unit_price": "可含'待报价'", "delivery_date": "YYYY-MM-DD|null",
 "sample_flag": "打样|大货|无", "status_hint": "沟通中|已报价|已确认|生产中|已交付|null",
 "task_content": "", "owner": "", "task_deadline": "YYYY-MM-DD|null",
 "source_excerpt": "支撑本结论的原文片段，≤100字"
}]
```
原则：只依据原文；两人对话注意上下文归属；出现"改成/变更为/加到"视为变更线索。

## 5. 校验规则（确定性，防幻觉）
- qty 转 int 失败→null；delivery_date 正则 `^\d{4}-\d{2}-\d{2}$` 校验，失败→null。
- order 行缺 customer 或 product → 丢弃并记入 skipped（结束文案提示"有 1 条信息不全待人工确认"）。
- 生成 order_id / task_id。

## 6. 变更比对逻辑
- 库内命中同 customer+product 且 status≠已交付 → UPDATE：仅覆盖本次有值的字段；old→new 追加进 changes（time=当前，source=source_excerpt）。
- status 取"更高阶段"（沟通中<已报价<已确认<生产中<已交付）；允许回退仅当原文明确。
- 无匹配 → INSERT 新订单。

## 7. 查询逻辑（防幻觉）
- 口语查询 → 解析意图（客户/产品/状态/时间区间）→ SELECT（customer LIKE 模糊匹配）。
- 0 条 → "台账中没有找到…可尝试换称呼或查看全部在途订单"。
- ≥1 条 → 口语化生成，**每条结论后必须附「依据：{source_excerpt}」**，只陈述表内事实，不补表外信息；多条用列表，先客户产品，再状态数量交期，最后给一句主动建议（如临期提醒）。

## 8. 简报聚合（数值全部来自查询，LLM 不得编数）
- 今日新增订单(created_at 当天)
- 待报价订单(status=沟通中)
- 临期交付(delivery_date≤未来3天 且 status≠已交付)
- 逾期任务(task.status=待办 且 deadline<今天)

## 9. 演示脚本（7 分钟 / 5 场景）
| 场景 | 内容 |
|---|---|
| 1 乱中取单 | 贴三段交叠群聊（含打断、改需求）→ 秒出 2 单 + 3 任务，强调"原文摘录可溯" |
| 2 随口查 | "万博那单什么状态？""这周有哪些要交付？"→ 口语查询带依据 |
| 3 变更捕获 | 追加"客户改数量"新消息 → 识别变更、更新订单、履历留痕 |
| 4 任务台账 | 可问"今天有哪些事没办" |
| 5 今日简报 | 一句话生成简报（新增/待报/临期/逾期） |

## 10. 自测清单（10.23 联调用）
- [ ] 三段交叠群聊 → 正确产出 2 单 3 任务，无幻觉字段
- [ ] 缺信息消息 → 不入库，提示人工确认
- [ ] 变更消息 → UPDATE 且 changes 留痕，状态只进不退
- [ ] "万博那单到哪了" → 回答含原文依据
- [ ] 简报数字与数据表逐条对得上
- [ ] 全流程录屏 + 模拟数据 JSON 备份

## 11. 代码模块对照（概念 → 文件）
| 概念 | 实现文件 |

| 订单/任务台账 | `store.py` 本地 JSON 存储（含查询/过滤） |

| 知识库（可选） | `data/` 下规格表，检索增强 |
