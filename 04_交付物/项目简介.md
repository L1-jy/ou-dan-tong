## 二、短版简介（约 150 字 · 报名表 / 展板用）

温州大量中小制造与贸易企业，订单信息活在微信群里：客户一句「数量加到 300，周五要」，跟单员就得翻半天记录。沟通是碎片化的，信息是口语残缺的，同一件事还反复变更——谁也说不清哪个是最新版本。

**瓯单通**是一个微信群聊订单协同智能体。它自动从聊天记录中抽取客户、产品、数量、交期与任务，记录每一次变更并维护唯一最新状态；用户一句话询问，直接返回最新进度而非过期旧信息。不改员工习惯、不依赖 ERP，让企业用最熟悉的微信群，也能拥有实时可靠的订单台账。

## 三、标准简介（约 500 字 · 提交材料正文）

### 问题：订单活在聊天里，协同活在人工里

温州的中小制造与贸易企业（机械配件、电气、鞋服等）普遍没有 ERP，或虽有 ERP 却覆盖不到「沟通」这一环。真实业务是这样流转的：

- 客户在群里说「法兰盘那单改 300 件，周五要」——一条口语消息，就是一次订单变更；
- 车间在另一个群说「3 号机轴承那单先缓缓」——一条随手提醒，就是一次任务调整；
- 跟单员要同时盯十几个群，靠人脑记住「哪句是最新的」。

由此产生四类典型失效：**信息散落无人汇总、口语残缺难成结构、反复变更状态失真、查询只能靠问且答不准**。业务员的应对方式往往是「再问一遍客户」，跟单员的日常是「逐条翻聊天记录」。这不是管理问题，是工具缺位。

### 方案：让智能体替人「读群、记账、答问、把关」

瓯单通定位为企业微信群的「订单协同副驾」，一条链路四步闭环：

1. **自动抽取**：从群聊原文识别客户、产品、数量、交期、任务，生成结构化订单与任务记录；
2. **变更留痕**：同一事项的多轮变更自动关联，只维护当前最新状态，同时保留完整变更履历与原文溯源；
3. **最新查询**：一句话问「那单到哪了」，直接返回最新版本，而不是某条过期旧消息；
4. **异常把守**：信息缺失时主动追问补齐、前后矛盾时标红提示、明显异常时拦截不入库。

### 价值：不改变习惯，不增加系统

对企业而言，它不要求员工学新软件、不要求上线 ERP、不要求改变在微信群里的沟通方式——**智能体迁就人的习惯，而不是让人迁就系统**。原本「必须靠人记住」的订单状态，变成「随时可查、有据可查」的组织资产，直接减少漏单、错单与重复确认的沟通成本。

### 技术实现

采用 Python 标准库实现的零依赖网页智能体：前端为可交互的群聊导入与台账界面，后端由「LLM 抽取 → 确定性校验 → 变更比对 → 台账存储 → 查询应答」五个模块组成。**LLM 负责理解口语，规则负责把守底线**——抽取交给大模型，冲突检测、异常拦截与状态合并用确定性代码实现，保证结果可解释、可复现、不随模型波动。演示环节全部使用模拟群聊数据。

## 四、详细简介（约 900 字 · 路演讲稿 / 方案说明素材）

### 4.1 背景与切入

本届瓯客松「AI＋企业智能体」赛道要求参赛者面向真实企业场景构建可运行的智能体。团队选择方向 07「碎片化沟通中的订单与任务协同」，原因很直接：这是温州本地产业最普遍、最日常、也最被工具忽视的一环。

温州中小企业的订单协同高度依赖微信——客户、业务员、车间、仓库在多个群里来回交接。沟通本身没问题，问题在于**沟通产生的结果没有被结构化沉淀**：一句口语化的变更，就足以让整条订单链路的状态失真，而系统里没有任何地方记录这件事。

### 4.2 核心痛点

| 痛点   | 具体表现                    |
| ---- | ----------------------- |
| 信息散落 | 订单与任务随聊随丢，散落在多个群，无统一台账  |
| 口语残缺 | 表达非正式、多别称、信息不全，无法直接结构化  |
| 反复变更 | 同一事项多次交接迭代，说不清哪个是最新版本   |
| 查询靠问 | 一句「那单到哪了」，翻半天记录仍给不出准确进度 |

### 4.3 解决方案

**瓯单通**（Order · Task · Coordination Agent）把群聊当作数据源，把台账当作输出：

- **读群**：接入群聊文本，逐条识别其中隐含的订单要素与任务指令；
- **记账**：生成结构化订单/任务记录，同一事项多轮变更自动归并到同一主键下；
- **留痕**：每次变更记录「谁、何时、从什么改成什么、依据哪句原文」，可回溯、可审计；
- **答问**：自然语言查询直接命中最新状态，并给出变更履历而非单条旧消息；
- **把关**：缺失信息反向追问，矛盾冲突标红，明显异常（如数量为负、交期早于下单日）拦截。

### 4.4 差异化亮点

1. **不做又一个 ERP，做 ERP 之前的那一层**——企业不需要更换系统，智能体寄生在既有沟通工具上。
2. **LLM 与规则分工明确**——大模型只做「理解口语」这件它擅长的事；状态合并、冲突判断、异常拦截全部由确定性代码完成，避免模型幻觉污染台账。
3. **变更是一等公民**——多数工具只存最终值，瓯单通同时存「变更过程」，既服务查询也服务追责。
4. **零依赖可运行**——单个 Python 进程即可启动完整演示，评委可现场导入群聊文本、现场提问验证。

### 4.5 进展与演示

项目已完成可运行原型：群聊文本 → 自动抽取 → 变更比对 → 台账存储 → 查询应答 / 日报简报的全链路已打通，并配有管线自测脚本。演示数据为团队自建的模拟群聊（覆盖新建订单、多次迭代更新、信息缺失、矛盾冲突、明显异常五类场景，含动态演进样本），不涉及任何真实企业数据。

### 4.6 团队与分工

团队四人均为计算机科学与技术专业大二学生，日常使用 AI 工具协作开发。分工按模块划分：模拟数据构建与变更识别（队友A）、测试验证（队友B）、查询应答（队友C）、状态维护（队友D），交付物制作按节点另行分配。
